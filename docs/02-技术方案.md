# 02 · 技术方案

> 面向 0→1 创业团队（初期 3–8 名工程师）的可落地架构。原则：**能少一个组件就少一个**，把复杂度留给真正的差异化（Agent 编排、送达率、合规），而不是留给基础设施。

---

## 一、架构总原则

| 原则 | 具体决策 | 理由 |
|---|---|---|
| **Monolith First** | 后端起步为**模块化单体**（清晰的模块边界 + 单一部署单元），只把 3 个天然异步的部分独立出去：Agent Runtime、发送执行器、站群构建器 | 3–8 人团队做微服务是自杀。模块边界画清楚，将来拆分成本可控 |
| **单一事实来源** | 所有业务对象落 PostgreSQL；分析型查询走物化视图，量大后再引 ClickHouse | 早期引数仓 = 双写 + 不一致 + 运维负担 |
| **事件驱动集成** | 模块之间通过领域事件解耦（`InquiryReceived`、`LeadScored`、`EmailBounced`） | Agent 与自动化天然是事件消费者；也为将来拆服务留好缝 |
| **工作流引擎承载长流程** | Agent 计划、多渠道序列、订单跟催用 **Temporal** | 这些流程跨天跨周、需要重试/补偿/人工介入。用 cron + 状态字段实现 = 无尽的边界 bug |
| **多区域部署** | 国内区（用户访问、数据主库）+ 海外区（访问 Google/Meta/LinkedIn/邮件 ISP） | 合规与网络可达性的现实约束 |
| **默认合规** | 合规校验做成**发送路径上的强制拦截器**，不是业务代码里的 if | 靠自觉一定会漏 |

## 二、技术选型

### 前端

| 项 | 选型 | 说明 |
|---|---|---|
| 框架 | **React 18 + TypeScript + Vite** | 生态与招聘面最好 |
| 组件库 | **Ant Design 5**（企业中后台）+ 自建设计 token 层 | 表格/表单密集型系统，AntD 省下大量工作；token 层保证将来可换肤 |
| 状态/数据 | **TanStack Query**（服务端状态）+ Zustand（少量 UI 状态） | 避免 Redux 样板 |
| 表格 | AntD Table + 虚拟滚动（线索表可达十万行） | |
| 图表 | ECharts（含地图，外贸场景需要国家分布） | |
| 富文本/邮件编辑 | TipTap + 邮件安全 HTML 白名单 | 邮件 HTML 有特殊约束（table 布局、内联样式） |
| 国际化 | i18next，UI 中/英，内容多语种 | 客户团队可能有外籍成员 |
| 实时 | WebSocket（新询盘、Agent 运行进度） | |
| **体验版（本仓库）** | **零依赖原生 ES Modules + 手写 SVG 图表** | 纯静态，可直接发 GitHub Pages，无构建步骤 |

### 后端

| 项 | 选型 | 说明 |
|---|---|---|
| 主语言 | **Go**（业务与集成）| 并发/IO 密集（大量邮件、抓取、API 调用），部署简单，内存占用低 |
| 备选 | Java + Spring（若团队背景是 Java）| 关键是**团队最熟**，不要为了时髦选型 |
| Web 框架 | Go: Echo / Gin；分层：handler → service → repository | |
| AI 服务 | **Python**（FastAPI）单独一层：LLM 网关、RAG、评分模型 | Python 的 AI 生态不可替代 |
| API | REST + OpenAPI 生成 TS 客户端；实时用 WebSocket | GraphQL 对小团队是净负担 |
| 认证 | OIDC + JWT，RBAC + 数据行级权限（私海隔离） | |

### 数据

| 组件 | 用途 | 备注 |
|---|---|---|
| **PostgreSQL 16** | 业务主库 | 多租户用 `tenant_id` 行级隔离 + RLS；大客户可单库 |
| **pgvector** | 知识库向量检索 | 早期不引专用向量库，Postgres 够用到百万级 |
| **Redis** | 缓存、限流、分布式锁、发送配额 | |
| **OpenSearch** | 线索/联系人/邮件全文检索 | 海关数据量大，Postgres 全文不够 |
| **ClickHouse**（阶段二） | 事件流分析、归因计算 | 事件量 > 1 亿/月 时引入 |
| **S3 / OSS** | 附件、素材、站点产物、单证扫描件 | |
| **Kafka / NATS** | 领域事件总线 | 起步可用 NATS（轻），量大换 Kafka |
| **Temporal** | 长流程编排 | Agent 计划执行、序列、订单跟催 |

### AI 层

```
┌─────────────────────────────────────────────────────────┐
│  Agent Runtime  (Python / FastAPI + Temporal Worker)     │
│  ┌──────────┬────────────┬──────────┬─────────────────┐ │
│  │ Planner  │ Tool Router│ Memory   │ Guardrails      │ │
│  │ 目标→计划 │ 工具调用   │ 短期+RAG │ 预算/限速/合规   │ │
│  └──────────┴────────────┴──────────┴─────────────────┘ │
├─────────────────────────────────────────────────────────┤
│  LLM Gateway  多模型路由 · 成本核算 · 缓存 · 降级          │
│  Claude / GPT / Gemini / 通义 · 按任务类型与成本路由        │
├─────────────────────────────────────────────────────────┤
│  Tool Registry (MCP 协议)                                │
│  customs.search · linkedin.enrich · maps.search           │
│  email.send · whatsapp.send · quote.calc · pi.generate     │
│  site.deploy · seo.audit · kb.retrieve                     │
└─────────────────────────────────────────────────────────┘
```

**关键设计**：

1. **模型无关**。所有 LLM 调用经网关，按任务类型路由（写作用强模型、分类打标用小模型、批量评分用本地小模型），按租户核算成本。模型换代不改业务代码。
2. **工具用 MCP 协议注册**，客户可接入自己的 ERP/PLM 作为 Agent 工具。这是生态位。
3. **Guardrails 是硬拦截**：每次外发前检查 opt-in 状态、退订名单、发送配额、内容合规（禁词/夸大宣传/价格泄露）。检查不通过则任务挂起等人工，不是记个日志放行。
4. **成本控制**：每租户每 Agent 有 token 预算；超限降级模型或暂停并通知。AI 成本必须能算到单客户单任务。
5. **可回放**：每个 Step 记录 `{input, tool, params, output, model, tokens, cost, latency, decision_reason}`。这既是审计需要，也是产品改进的数据来源。

### 外部集成

| 集成 | 方案 | 风险与对策 |
|---|---|---|
| 邮件收 | IMAP + Gmail/Outlook OAuth | OAuth 应用审核周期长，提前启动 |
| 邮件发 | 自建 MTA（Postfix + 多 IP）**或** AWS SES / Postmark | 起步用第三方（信誉即时可用），量大后自建降本。**必须多域名池 + 身份隔离** |
| 送达率 | DMARC 报告解析、Google Postmaster API、退信/投诉回环（FBL） | 域名信誉毁掉难恢复，必须强制限速与自动预热 |
| WhatsApp | **WhatsApp Business Cloud API（官方）** | 绝不用非官方协议库——封号且违反 Meta 条款。模板需审核，opt-in 需留证 |
| LinkedIn | 官方 API 能力有限；辅助动作走**用户自有账号 + 人工确认 + 严格限速** | 高风控风险。产品上明确告知用户风险，默认保守频率 |
| 海关数据 | 采购第三方数据商 API（腾道/贸小七等），做**统一抽象层** | 单一供应商锁定风险；抽象层允许多源切换与比价 |
| 站群部署 | **Astro（SSG）** 构建 → Git 提交 → CDN（Cloudflare Pages / OSS+CDN）| 静态产物安全、快、便宜。母子站 hreflang/canonical 自动生成 |
| 汇率 / 物流 / 支付 | 汇率 API、船公司追踪 API、PingPong/连连（外贸收款） | |

## 五、关键子系统的工程细节

### 5.1 送达率子系统（护城河之一）

```
发送请求 → [合规拦截器] → [配额与预热限速器] → [域名池路由] → MTA/SES → ISP
              ↓ 拒绝            ↓ 排队/降速         ↓ 选身份
          挂起待人工          按曲线爬坡        冷开发 vs 交易邮件隔离
                                                     ↓
                          反馈回路 ← 退信/投诉/FBL/DMARC报告/Postmaster API
                                        ↓
                          健康分下降 → 自动降速 / 暂停该域 / 告警
```

- **预热曲线**：新域第 1 天 20 封 → 第 30 天 500 封，按打开率动态调整，用户无法绕过
- **身份隔离**：交易类邮件（PI、订单通知）走主域；冷开发走专用子域。主域信誉是公司资产，不能被开发信毁掉
- **健康分**：0–100，由认证配置、退信率、投诉率、打开率、域名年龄加权

### 5.2 合规拦截器（横切）

作为**发送路径上唯一出口**，任何代码路径都无法绕过：

```go
func (c *ComplianceGate) Check(ctx, msg) (Decision, error) {
    // 1. 全局退订名单（跨租户内所有序列/账号）
    // 2. 渠道级 opt-in 状态（WhatsApp 营销消息必须有证据）
    // 3. 地域规则（EU 收件人 → 要求关联 LIA 记录）
    // 4. 页脚注入（公司名/地址/退订链接/联系原因）
    // 5. 内容检查（禁词、误导性宣称、价格泄露）
    // 6. 频率上限（同一联系人 N 天内不超过 M 次）
    // → 通过 / 修正后通过 / 挂起待人工 / 拒绝并记录
}
```

### 5.3 Agent 执行的可靠性

- **幂等**：每个 Step 有幂等键，Temporal 重放不会重复发信（发信是不可逆动作，必须最强保护）
- **预算护栏**：Goal 级 token 与金额上限，超限暂停并通知
- **超时与降级**：外部 API 超时降级到缓存结果或跳过该步骤，不阻塞整个计划
- **人工接管**：任何 Task 可 `pause → 人工编辑输入/输出 → resume`
- **回放**：基于 Event 全量记录重建执行过程，供审计与调试

### 5.4 多租户与数据隔离

- Postgres RLS + `tenant_id` 强制注入（在 repository 层统一处理，禁止业务代码手写 tenant 条件）
- 私海隔离在**行级权限**实现，不是前端过滤
- 附件与素材按租户前缀存储，签名 URL 有效期 ≤ 15 分钟
- 敏感字段（客户邮箱、电话）**字段级加密**，密钥 KMS 托管；导出行为强审计

## 六、体验版（本仓库）技术说明

体验版是**纯静态前端**，目标是零构建、零依赖、可直接托管于 GitHub Pages。

| 项 | 实现 |
|---|---|
| 结构 | 原生 ES Modules（`<script type="module">`），无打包器 |
| 路由 | Hash 路由（`#/dashboard`），**与部署路径无关**——放在 `/ems`、`/exportmarketingsystem` 或域名根目录都能跑 |
| 样式 | 单个 `app.css`，CSS 变量做设计 token |
| 数据 | `assets/js/data.js` 内置模拟数据（客户、线索、订单、Agent 运行日志等） |
| 图表 | 手写 SVG（折线/柱状/环形/漏斗/热力），无第三方库、无 CDN 依赖 |
| 资源 | 全部本地，无外链字体/脚本 → 离线可用、无隐私外泄、加载快 |
| 角色 | 顶部可切换「业务员 / 老板」，两套工作台与导航权限 |

**为什么体验版不用 React**：目标是让任何人 clone 后双击就能看、GitHub Pages 一开就能发，不需要 Node 环境和构建流水线。正式产品用 React + Vite（见上文选型）。

## 七、非功能性要求

| 维度 | 目标 |
|---|---|
| 可用性 | 核心 API 99.9%；发送执行器故障不影响 CRM 读写 |
| 性能 | 列表页 P95 < 800ms（十万行虚拟滚动）；收件箱首屏 < 1.5s |
| 数据安全 | 传输 TLS 1.3；静态加密；字段级加密敏感 PII；操作全审计 |
| 合规 | GDPR 数据主体请求（导出/删除）≤ 30 天完成，系统提供一键流程 |
| 备份 | Postgres PITR，每日全量 + WAL 归档，异地保留 30 天 |
| 可观测 | OpenTelemetry 全链路；Agent 成本与 token 单独看板 |
| 灾备 | RPO ≤ 15 分钟，RTO ≤ 4 小时 |

## 八、主要技术风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| LinkedIn / WhatsApp 平台风控 | 客户账号被封，信任崩塌 | 只用官方 API；LinkedIn 走用户自有账号 + 保守限速 + 风险明示；产品不承诺规避风控 |
| 域名信誉被毁 | 客户邮件全进垃圾箱 | 强制预热与限速（不给用户自毁按钮）、多域名池、身份隔离、健康分自动熔断 |
| 海关数据供应商锁定/涨价 | 成本失控、能力受制 | 统一数据抽象层，支持多供应商切换与比价；缓存已查数据 |
| LLM 成本超预期 | 毛利被吃掉 | 多模型路由 + 小模型做批量任务 + 结果缓存 + 租户级预算硬上限 |
| AI 生成内容失实伤害品牌 | 客户流失、法律风险 | 强制人工把关门（L1 默认）、事实引用来自产品库、生成内容标注来源 |
| 跨境网络与合规（数据出境） | 无法交付或违规 | 多区域部署；数据出境走合规路径；提供数据驻留选项 |
| 单体膨胀 | 迭代变慢 | 模块边界 + 领域事件；当某模块团队 > 3 人或部署频率显著不同则拆分 |
